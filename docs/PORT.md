# HamQuest port record

The original was written by the user between 2007 and 2011 (a WinForms app, then a Silverlight port, then an attempted WPF port that was abandoned); this port is from October 2026.

Decisions and findings log, in the style of Kordanor's Cabal's `PORT.md`. Plan: `PORT_PLAN.md`. Rules: `game-reference.md`.

## Decisions

- **D1 Fidelity: modernise freely.** C# is a design reference. Log each departure.
- **D2 Content: generate Odin tables** from XML + CQM at build time.
- **D3 Audio: none in v1.** Provenance of the samples unconfirmed. **Art provenance settled by the user (2026-10-11):** David Gervais's 32x32 Angband graphics (CC BY 3.0, attribution required; https://angband.readthedocs.io/en/latest/copying.html) and the user's own doors and walls.
- **D4 Extras in v1:** save/resume, touch controls, `?seed=N`.
- **D5 Rendering: framebuffer + packed atlas** (A1/A2 in the plan). Page only stretches the frame.
- **D6 Maze: fixed 8x8**; size stays a single generator constant.
- **D7 Balance: tune as I go.** Rules are tuned while implementing M4, not held for M8; every change is logged here with the old and new value so regressions stay distinguishable.
- **D8 Native SDL2 client: yes.** A second platform shell (`odin/platform/native`) over the same core, in the style of Murder Hobo. Core stays free of platform imports; audio and file IO sit behind the services struct.
- **D9 Name: "HamQuest of SPLORR!!"** (itch.io and vault). Repo and code keep `hamquest`.
- **D10 Vault note now; 640x560 logical size, landscape, integer scaling**; phones landscape with side touch controls.
- **D11 Shop prices: charge the displayed price.** Fixes the `uint`-from-`int` bug (original charged 0). Prices in the data run 25 to 1,000; treasure and stock may be retuned under D7.
- **D12 Blocked moves cost a step: keep.** Any arrow key counts as a step, as in the original; Space remains the deliberate pass.
- **D13 Tutorials: keep first-time pop-ups with a persistent "stop tutorial"** (remembered in localStorage and the save). `always-tutorial` messages still show. No separate help screen in v1.
- **D14 Lethality confirmed from the user's play memory:** a new character in the original was this brutal. The port's M4 rules are therefore right as they are; the bot's early deaths are not a porting bug.
- **D15 Difficulty: keep the original** (no Easy option, no softened opening) for v1. Revisit only if playtesting shows it is unplayable cold; tutorial pop-ups carry the guidance.
- **D16 Next: M5 renderer and HUD**, with the native SDL2 window (D8) so feel can be judged early; no text harness.
- **D17 Fit to window:** the itch.io page launches full screen, so the web build scales the picture to the best fit of the window (whole-number nearest-neighbour enlargement, then a smooth resize to the exact fit), not whole-number steps only.

### M1 (in progress)
- **[CHECK] items resolved from the data (not from play):** (a) speed: player `speed-roll` is 2 to 12 moves per turn, scaled by armour (boots x2.0, clothes/chainmail x0.75, platemail x0.5, helmet/shield x1.0), and creatures get `speed / playerSpeed` steps per player move; so plate is slow *and* lets monsters act more often per move. Direction is consistent, so port as written. (b) The Amulet drops **only** from the Necromancer (`item-drops`, 100%; `item-count` 0, placement None). While carried it blocks portals and portal-monster teleports but also blocks the exit; `Y` drops it and teleports you. A boss reward with a trade-off, not a curse. Keep.
- `docs/game-reference.md` drafted from code. Findings with consequences for the port:
  1. **The maze is a spanning tree.** All locks sit on leaf portals and all keys on non-leaf cells, so key/door ordering is solvable by construction. Port generation tests can assert this instead of solving.
  2. **Shopping is free** (price read as `uint` from an `int`; exception swallowed). Decision needed: keep, or charge the displayed price. Affects economy and whether gold matters at all beyond thieves.
  3. **`SpawnMonsters` can hang** when no visited cell has a trap or no `spawns` item is present. The port needs a defined fallback (spawn at a random free interior tile).
  4. **A blocked move still ends a step** (step tracker is advanced by the UI after any arrow key). Probably intended (walls cost time) but changes light burn and monster speed; confirm.
  5. Hard-coded item names in the rules: `Amulet`, `RainbowKey`, `Tools`, `Quest`, `Gold`. The generator should expose them as constants and fail if missing.
  6. Creature speed is relative to the player's rolled speed; heavier armour *slows the player's turn clock*, which makes monsters faster per move. Verify direction with the user before porting the formula.
- Not verified: everything in the reference marked **[CHECK]**; no values (item stats, creature stats) are in the doc yet, they will come from the generator (M2).
- Not yet reviewed: `Maps/Map.cs` creature placement tail, `PlayerMessageStatistics`, `ThemeTable`, `TerrainTable`, `MessageTable` (themes may swap images; check).

### M3 world generation (2026-10-10)
- Done: `odin/game/` (package `game`, imports only `content`; type-checks for native and `js_wasm32`): `rng.odin` (xoshiro256** seeded by splitmix64, unbiased bounded ints, `pick_weighted`), `world.odin` (fixed-size `World`: shared `Portal`s, `Maze_Cell` with its `Map`, `Tile{terrain,item,creature}`, creatures, player, rolled start inventory), `generate.odin` (`generate(^World, seed) -> Gen_Error`). No heap, no globals; a world is one flat struct.
- Order: portals, Prim spanning tree, room/passage by `ROOM_CHANCE_BY_DOORS`, terrain blend, locks on dead ends with the door item placed in the neighbour on the facing side, keys in non-dead-end cells, items by `item_count`/placement, creatures, player in a non-dead-end cell, start inventory.
- Departures from the C# (D1): every placement search is bounded (200 random tries, then a deterministic scan, then a `Gen_Error`); direction choices in Prim's are uniform over valid neighbours instead of retry loops; doors are placed before anything else so they can never be blocked; the player is placed last (after items and monsters), where the original placed it among a cell's creatures in table order; revisit if starting next to a monster feels unfair (D7).
- Verified (native, 200 seeds unless noted): RNG matches an independent Python implementation; same seed gives a byte-identical world, different seed a different one; open portals = 63 and connected (spanning tree); every dead end's single portal is locked, no other portal is; each lock has exactly one door in the neighbour at the doorway tile facing it and with the lock type; keys per type = locks per type and none in a dead end; item tiles (excluding doors/keys) = sum of `item_count`, all on passable tiles; exactly 1 Exit and 16 Quest items, all in dead ends; creature count = sum of `creature_count`, all on interior passable tiles; player not in a dead end on a free tile; every doorway tile is passable iff its portal is open; spawn_as chains have no cycles (static check over the content).
- Measured over 100 seeds: avg 22.6 dead ends and 46.2 rooms of 64 cells, 764 item tiles, 193 creatures per world; longest random search 24 tries; 0 fallback scans.
- Not verified: statistical equivalence with the C# distribution (placement uses the same rules but a different RNG and a different call order); that 193 monsters per 64 rooms matches the feel of the original.
- Things to know for M4: movement across cell edges uses the doorway tiles at (7,0) (14,7) (7,14) (0,7); `Tile.creature` is `index+1` into `World.creatures`; applying `start_inventory` (durability, auto-equip) is M4 work; `World.cells[row][col]` is row-major, `Map.tiles[row][col]` likewise (the C# was column-first).

- Departures from the C# (D1), beyond M2/M3: thief that steals a quest piece now says so (the original reused the "gain experience point" message); pathing is recomputed after a teleport (the original left stale distances so monsters wandered until the next step); spawning from a quest piece picks uniformly among spawn-tagged tiles on visited cells and stops when they run out (the original could loop forever); inventory iteration is in item-table order (the original used dictionary order, which only mattered for ties); `Shop` items vanish when visited because the data never set `shop-behavior` (so the original's switch matched nothing and the item was cleared); the player is not a creature on the tile grid (monsters compare coordinates instead).

### M7 saves, touch and fit-to-window (2026-10-11)
- **Saving by replay.** A save is the seed plus the commands that took effect, one character each (`n e s w r y t x`, `b`/`B` + slot digit for shop buys), as strict JSON with `format`, `version`, `rules` (hand-bumped `RULES_VERSION`), `content` (a hash of the generated rules data, emitted by `gen_content.py` as `CONTENT_HASH`), the seed, the tips seen and the stop-tips choice. Typical size 200 to 3,000 bytes. Because the engine is deterministic and identical on native and wasm (parity-tested), a save made on one restores on the other. The price: a save only fits the rules and content it was made with; any other is refused as `Incompatible` rather than guessed at. A finished game, or a log that overflowed (200,000 commands), is stored as `{"format":"hamquest-save","version":1,"empty":true}` (the page never deletes the key, so an older save cannot come back).
- Decoding is strict (exact shape, hex digits, command grammar, length caps) and **changes nothing unless the result is Ok**; replay is bounded by the log cap. Tests: round trip restores a byte-identical `World` and the two games then stay identical; empty marker; truncated, wrong format, future version, illegal command, shop letter without slot, other content hash, trailing junk are all refused without touching the running game.
- **Web:** `localStorage` key `hq:save` (namespaced; itch.io games share one origin), written at most once a second after a change and when the page is hidden; `?seed=N` plays that world and does not touch the stored save; a damaged or foreign stored value is left alone until the next save overwrites it. **Native:** `hamquest.save` in the working directory (`--save-file`, `--no-save`; `--seed` means a fresh game and no saving).
- **Touch and mouse:** `ui.app_tap(x, y)` (tap toward a direction on the map, on yourself to rest, tap shop rows and buttons, tap to dismiss tips and to restart after a game, tap the attack/defend icons) plus HTML buttons on touch devices (`?touch=1` forces them): a direction pad with Rest on the left, OK/Esc/Mode/Amulet/New on the right, directions repeat while held. Landscape layout verified at 812x375 in the browser pane.
- **Fit to window (D17):** the picture is enlarged by a whole number (nearest neighbour) to at least the size the screen needs and the browser resizes that canvas smoothly to the exact fit; verified at 1600x900 (canvas 1028x900 from a 1280x1120 buffer). `F` toggles full screen; the itch.io full-screen launch needs nothing else.
- **Verified:** 59 tests (8 new: save round trip, empty marker, rejection cases, overflow, shop commands logged, tap moves/rest, tap in shops/tips, tap mode toggle); reload in the browser pane resumed the same game with an identical frame hash; native writes and reads `hamquest.save`.
- **Bug found by a test:** `rng_below` looped forever on an all-zero generator state (an uninitialised world); the rejection loop is now bounded. A good reminder that every loop in the core needs a bound (D1).
- **Not verified:** real phone touch (only the pane's emulation and synthetic presses), localStorage inside the itch.io iframe (browsers may block third-party storage in some privacy modes; the code survives it and just does not save), very long games (a 200,000-command log replays in well under a second natively but not measured in wasm).
